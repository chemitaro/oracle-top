# 技術境界の決定記録

状態: 正式版（2026-09-30採用）。同一会話のStrict相談をローカルOracle根拠へ照合済み。本体は未実装です。

以下のD-01〜D-08で、根拠資料に挙げられた境界をすべて決定します。これらは追加機能ではなく、既存MVPの入力・出力・失敗時挙動の具体化です。根拠資料の境界一覧は `oracle-evidence.md` の30〜37行に対応します。

| 決定 | 対象 | 採用する規則 |
|---|---|---|
| **D-01** | browser判定、API/Gemini除外、未知model、mode欠損 | 明示的なbrowser modeとChatGPTの肯定根拠を要求します。API/Geminiの明示的根拠があれば除外します。mode欠損をmodelやURLから補いません。未知modelはChatGPT URLの根拠があれば保存名のまま対象にします。 |
| **D-02** | home/profile、複数profile、異なるmax、JSON5 | homeとprofileは独立です。台帳は選択した1profileだけ、セッション集計は選択home全体です。保存profileが不明なセッションを、選択profile所属とは推定しません。max競合は同profileの最新開始候補を採用し、警告します。 |
| **D-03** | 日時、窓端、不正・未来、分母0 | timezone付きの限定ISO形式を検証します。窓は両端を含みます。不正・欠損は定義済みfallback、未来の有効日時はfallbackせず集計除外です。未来の開始時刻のelapsedは `null`、分母0のsuccessも `null` です。 |
| **D-04** | effort順、alias、follow-up | 保存名はtrim以外変更しません。`high` は `extended` と `standard` の間に置きます。follow-upは初回boolean trueを必須とし、completedかつ配列全体が有効な場合だけ長さを加算します。 |
| **D-05** | 安全read、更新競合、破損、symlink、制御文字 | 直接read、1ファイル1MiB、最大8並行です。配下symlinkは拒否し、更新検出時は当該ファイルだけ隔離します。JSON/JSON5の未知キーは無視し、表示・JSON出力では制御文字を安全化します。 |
| **D-06** | 幅、高さ、単発出力、非TTY、終了 | TUIだけをviewportへ収めます。保護列が収まらなければ明示的なサイズ不足表示です。高さ不足は表別の省略件数を表示し、単発テキスト／JSONは全件を返します。非TTYのTUI起動はexit 2です。 |
| **D-07** | poll、CPU、メモリ | 初回即時、既定2秒、採取・描画の非重複、遅れたtickは追いかけません。resizeでは再採取しません。1,000件の固定fixtureでCPU・RSS・採取p95を検証します。 |
| **D-08** | 依存、配布、実装ゲート | Node 24／TypeScript ESM／軽量ANSIです。runtime直接依存はJSON5と表示幅ライブラリだけです。各段階で1振る舞いずつRed→Greenを行い、最終的にパッケージ導入、TTY、読み取り専用、性能、文書を検証します。 |

## ドラフトから明示的に修正する点

特に次の変更は、黙って解釈変更せず文書へ記録してください。

| ドラフト上の扱い | 採用規則 |
|---|---|
| 未来の開始時刻をelapsed 0へclamp | **`null`／`N/A`＋警告**にします。実際の経過0秒と区別します。 |
| sessions全体が読めなくても空配列・0件 | **セッション関連の3領域を `null`** にします。正常な空集合とは区別します。 |
| profile記録がなければmonitor profileへ割当て | **所属不明**とし、そのセッションのmaxを採用しません。 |
| effort `high` の位置が未定義 | `extended` の次、`standard` の前に固定します。 |
| 警告codeが任意文字列 | 後述の閉じたcode一覧に固定します。 |
| JSON.stringifyだけで端末安全と説明 | C1制御文字なども明示的にUnicode escapeします。 |
| 計画検査が9ステップ固定 | 今回の **P01〜P10** に合わせて検査を更新します。 |

相談前の計画検査はR-ID、9ステップ、Schemaと例の最上位キーだけを検査していました。正式版では10工程・8境界・49ケース・30 warning codeも検査し、完全Schema検査を別に実施しました。製品の動作検証は未実施です。

## 採用時の調整

- P01は文書採用工程として本タスクで完了します。文書編集のために製品テストのRedを作ったことにはしません。
- P02の開発基盤設定を写すだけのユニットテストは作りません。実コンパイルとESM出力で確認します。製品の振る舞いのTDDはP03から、統合TDDはP08以降で行います。
- 全体取得不能のnull、未来日時のnull、選択profile所属不明の除外、highの固定順位は、既存の表示対象・出力形式を変えずに不明値を明確にする技術判断として採用します。
- 残るProduct判断はありません。型定義やI/O adapterの局所的な実装形は、公開契約を変えない範囲で実装者が決めます。
